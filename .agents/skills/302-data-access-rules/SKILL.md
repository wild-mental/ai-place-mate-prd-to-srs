# 데이터 접근 규칙

프레임워크 사용법은 설치된 스킬 `prisma-client-api` · `prisma-database-setup` ·
`supabase` · `supabase-postgres-best-practices`가 다룬다.
**이 문서는 그 위에 얹히는 이 프로젝트의 결정**만 적는다.

## 연결 — 두 개를 헷갈리지 않는다

Supabase는 용도가 다른 두 포트를 준다. 잘못 쓰면 마이그레이션이 깨지거나
서버리스에서 커넥션이 고갈된다.

| 환경 변수 | 포트 | 용도 |
| --- | --- | --- |
| `DATABASE_URL` | `:6543` Supavisor 트랜잭션 풀러 | **애플리케이션 런타임.** 서버리스는 인스턴스가 많아 풀러가 필수다 |
| `DIRECT_URL` | `:5432` 직결 | **마이그레이션 전용.** 풀러는 DDL·advisory lock을 제대로 못 다룬다 |

`schema.prisma`에 둘 다 명시한다. 하나만 쓰면 반드시 한쪽이 고장난다.

## 마이그레이션

- 스키마 변경은 **항상 마이그레이션 파일로** 남긴다. `db push`는 로컬 실험에만
- 파괴적 변경(컬럼 삭제·타입 축소)은 두 단계로 나눈다 — 먼저 추가하고 쓰기 전환한 뒤 나중에 제거
- 로컬은 Supabase CLI로 띄운다. 운영 스키마와 로컬이 갈라지면 그때부터 신뢰할 수 없다

## RLS

- **모든 사용자 데이터 테이블에 RLS를 켠다.** 정책은 `supabase/policies/`에 파일로 둔다
- Service Role 키로 RLS를 우회하는 경로를 만들지 않는다.
  Cron·웹훅처럼 불가피한 경우만 쓰고, 그 범위를 코드 주석에 남긴다
- 새 테이블을 만들면 **정책도 같은 PR에** 넣는다. 나중에 붙이면 그 사이가 구멍이다

## 트랜잭션

- 경계는 도메인 모듈이 정한다. 진입점이 트랜잭션을 열지 않는다
- `$transaction` 안에서 외부 API를 부르지 않는다 — 락을 잡은 채 네트워크를 기다리게 된다
- 예약·결제처럼 외부 호출이 끼는 흐름은 **상태 머신 + DB 큐**로 쪼갠다

## 성능

- `select`로 필요한 컬럼만 가져온다. 목록 조회에서 관계를 통째로 `include`하지 않는다
- N+1을 만들지 않는다 — 루프 안의 쿼리는 리뷰에서 막는다
- 인덱스는 **실제 쿼리 형태를 보고** 만든다. 추측으로 붙이면 쓰기만 느려진다
- 무거운 집계는 실시간으로 돌리지 않는다. 집계 Cron(`app/api/cron/aggregate`)이 있다

## 안티패턴

| ❌ | 왜 |
| --- | --- |
| 런타임에 `DIRECT_URL` 사용 | 서버리스에서 커넥션 고갈 |
| 마이그레이션에 `DATABASE_URL` 사용 | 풀러가 DDL·lock을 못 다룸 |
| RLS 없이 사용자 테이블 생성 | 권한 우회 경로 |
| 트랜잭션 안에서 외부 API 호출 | 락 유지 시간이 네트워크에 종속 |
| `page.tsx`에서 Prisma 직접 호출 | 계층 침범 (스킬 `301`) |
