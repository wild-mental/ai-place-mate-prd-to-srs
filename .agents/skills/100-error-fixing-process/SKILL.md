# 에러 해결 절차

## 왜 절차가 필요한가

에러를 보면 바로 고치고 싶어진다. 그러면 **증상만 사라지고 원인이 남는다.**
아래 순서는 원인에 도달하기 전에 손대지 않기 위한 것이다.

## Step 1. 현상 정의

관측한 것만 적는다. 추측을 섞지 않는다.
- 무엇을 했을 때 무엇이 나왔는가 (실제 메시지·스택 그대로)
- 재현되는가, 간헐적인가
- 언제부터인가 — 최근 변경과 겹치는가

## Step 2. 범위 탐색

관련 파일·데이터 흐름·함수를 지도로 그린다. 아직 고치지 않는다.
- 어느 계층인가 — 진입점(Server Action·Route Handler) / 도메인 / 데이터
- 경계를 넘는가 — 외부 API · DB · LLM

## Step 3. 원인 특정

**증거와 함께** 좁힌다. "아마 이것 같다"는 원인이 아니다.
- 로그·스택·재현 조건으로 뒷받침한다
- 여러 후보가 남으면 각각을 배제할 실험을 정한다

## Step 4. 중급 개발자에게 설명하듯 요약

전문 용어를 걷어내고 한 문단으로 적는다.
여기서 설명이 안 되면 **아직 원인을 모르는 것이다.** 3단계로 돌아간다.

## Step 5. 수정 지점 제시

고칠 곳과 이유를 먼저 나열한다. 곧바로 코드를 쓰지 않는다.
- 최소 수정으로 끝나는가, 설계를 건드려야 하는가
- 같은 원인의 다른 발현 지점이 있는가

## Step 6. 수정

- 원래 의도를 보존하며 고친다. 이해 못 한 코드를 지우지 않는다
- 범위를 넘지 않는다. 눈에 띈 다른 문제는 따로 기록한다
- **재현 테스트를 먼저 쓴다** (스킬 `tdd`). 통과하지 않는 것을 확인하고 고친다

## Step 7. 후속 제안

- 같은 부류를 막을 테스트·타입·검증이 있는가
- 원인 파악이 오래 걸렸다면 관측이 부족한 것이다 — 로그를 보강한다
- 구조 문제면 태스크로 만든다. 지금 고치지 않는다

## 이 프로젝트에서 자주 나오는 것

| 증상 | 먼저 볼 곳 |
| --- | --- |
| 빌드가 `verify-constraints`에서 실패 | 제약 위반 — 스킬 `300-tech-constraints-guardrails` |
| 마이그레이션이 멈추거나 락 | `DATABASE_URL`/`DIRECT_URL` 혼용 — 스킬 `302-data-access-rules` |
| 커넥션 고갈 | 런타임에 직결 URL 사용 — 스킬 `302` |
| 캐시가 무효화되지 않음 | `cacheTag` 누락 — 스킬 `301-server-boundary-rules` |
| Server Action에서 GET 캐시가 안 먹음 | Server Action은 항상 POST — 스킬 `301` |
| RLS로 데이터가 안 보임 | 정책 누락 또는 잘못된 키 — 스킬 `302` |
| LLM 응답이 스키마와 다름 | 구조화 출력 미사용 — 스킬 `303-ai-integration-rules` |
| 프롬프트를 고쳤는데 옛 결과 | 파싱 캐시 미무효화 — 스킬 `303` |
