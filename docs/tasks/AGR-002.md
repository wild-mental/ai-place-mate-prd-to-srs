## 🧪 Acceptance Criteria (BDD/GWT)

Scenario 1: 제안이 폴링 없이 도착한다
- Given: 이용자가 대화방 채널을 구독한 상태에서
- When: 매장이 제안을 제출하면
- Then: Realtime 브로드캐스트로 즉시 전달된다. 클라이언트 폴링이 없어야 한다. **폴링 요청 0건**

Scenario 2 (실패 흐름): 연결이 끊겨도 상태가 어긋나지 않는다
- Given: 구독 중 네트워크가 끊겼다 복구된 상태에서
- When: 재연결되면
- Then: 현재 대화방 상태를 다시 조회해 동기화한다. 끊긴 동안 도착한 제안이 누락되어서는 안 된다.

Scenario 3 (실패 흐름): 다른 대화방을 구독할 수 없다
- Given: 자신이 참여하지 않은 `roomId` 가 주어지고
- When: 해당 채널 구독을 시도하면
- Then: RLS가 거부한다. 타인의 제안이 노출되어서는 안 된다.

## ⚙️ Technical & Non-Functional Constraints
- 기술 제약: **LIM-T01** 장시간 실행 프로세스를 둘 수 없다. **ADR-T06** DB 상태 + Realtime + lazy close 조합으로 해결한다.
- 보안: **REQ-NF-012** Realtime도 RLS 적용 대상이다. 익명 키로 임의 채널을 구독할 수 없어야 한다.
- 계층 분리: 이 태스크는 유형 `UI` 다 — 클라이언트 구독 코드이므로 기능 구현(BE)과 분리한다(원칙 P6).
- 의존: 실시간 전달이 **Supabase Realtime 가용성에 종속**된다(SRS §15-6). 장애 시 마감은 lazy close로 여전히 확정된다.
