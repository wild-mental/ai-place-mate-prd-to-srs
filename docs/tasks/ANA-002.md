## 🧪 Acceptance Criteria (BDD/GWT)

Scenario 1: 이벤트가 유실 없이 적재된다
- Given: 클라이언트가 `sendBeacon` 으로 배치를 보내고
- When: 수집 엔드포인트가 처리하면
- Then: 이벤트가 `occurredAt` 파티션에 적재되고 세션이 스티칭된다.

Scenario 2: 계측이 응답을 지연시키지 않는다
- Given: 서버 이벤트가 `after()` 로 적재되는 상태에서
- When: Server Action이 실행되면
- Then: 적재는 응답 이후에 수행되고 사용자 응답 시간에 포함되지 않는다. **계측으로 인한 지연 0ms (ADR-T07)**

Scenario 3 (실패 흐름): 중복 event_id가 이중 계수되지 않는다
- Given: 클라이언트 재시도로 같은 `event_id` 가 두 번 도착하고
- When: 수집이 처리하면
- Then: DB 기본 키 제약으로 두 번째가 폐기된다. 지표가 부풀지 않아야 한다. **이중 계수 0건**

Scenario 4 (실패 흐름): 계측 실패가 사용자 요청을 막지 않는다
- Given: 이벤트 적재가 실패하는 상태에서
- When: 사용자 요청이 처리되면
- Then: 요청은 정상 완료된다. 계측은 비동기·유실 허용 경로다 (SRS §7 계측 파이프라인).

## ⚙️ Technical & Non-Functional Constraints
- 성능: **REQ-NF-001a** 계측이 응답 지연 원인이 되면 안 된다. 서버 적재는 `after()`, 클라이언트는 `sendBeacon`.
- 기술 제약: **D-04 · REQ-TEC-014** 외부 메시지 브로커를 두지 않는다. 대가로 대량 유입 시 DB 쓰기 부하가 생긴다(SRS §15-10).
- 정합성: **48시간 지연 도착 허용 · D+2 확정.** 확정 전 값은 `provisional` 로 표기해 성급한 판단을 막는다.
- 보안: **REQ-NF-010** 이벤트 속성에 개인 식별 정보를 담지 않는다.
