## ✅ Task Breakdown (실행 계획)
- [ ] `Place` — `id` · `name` · `districtCode` · `seats` · `maxParty` · `latitude` · `longitude` · `deletedAt`(논리 삭제). `@@index([districtCode, deletedAt])`
- [ ] `Dish` — `placeId` · `name` · `canonicalKey` · `price`. **`@@index([canonicalKey])` 필수**
- [ ] `PriceProfile` — `perPersonLow` · `perPersonHigh` · `sampleSize`. **단일 값 컬럼을 두지 않는다**
- [ ] `Attribute` — `ownerId` · `scope`(PLACE/DISH) · `key` · `value`. **성분·접근성 필드를 같은 테이블에 사전 확보** (REQ-FUNC-010). `@@index([ownerId, scope, key])`
- [ ] `Verification` 을 **별도 엔터티로 분리** — `attributeId`(unique) · `status` · `verifiedAt` · `verifiedBy` · `sourceUrl`. `@@index([verifiedAt])` (ADR-002)
- [ ] `AgentRoom` · `Proposal` · `Reservation` · `Payment` — `Proposal` 에 **가격 필드 없음**, `Payment` 에 **카드 정보 컬럼 없음**, `idempotencyKey` unique
- [ ] `Event` — `eventId`(PK · 중복 제거 키) · `occurredAt` · `receivedAt` · `properties` · `incomplete`
- [ ] `Event` **일 단위 파티셔닝 원시 SQL 마이그레이션** 작성 (Prisma 스키마로 표현 불가)
- [ ] **`canonicalKey` 정규화 사전 및 정규화기** 구현 — '물냉면/평양냉면/냉면'을 동일 키로
- [ ] 시드 스크립트 — 가격 표본 5건 이상/미만 매장, 90일 초과 속성을 각각 포함
- [ ] 단위 테스트 — 논리 삭제 동작, `canonicalKey` 교차 매장 조회, 금지 컬럼 부재

## 🧪 Acceptance Criteria (BDD/GWT)

Scenario 1: 메뉴명 정규화 키로 여러 매장이 함께 조회된다
- Given: `canonicalKey = "냉면"` 을 공유하는 `Dish` 가 서로 다른 세 `Place` 아래 적재되어 있고
- When: `canonicalKey` 로 조회하면
- Then: 세 매장의 `Dish` 가 모두 반환되고 인덱스를 사용한다. `EXPLAIN` 에 Seq Scan이 없어야 한다.

Scenario 2: 속성마다 확인 이력이 정확히 하나 붙는다
- Given: `Attribute` 와 `Verification` 이 1:1로 정의된 상태에서
- When: 속성을 조회하면
- Then: `verifiedAt` · `verifiedBy` 가 반드시 함께 조회된다. 확인 이력 없는 속성이 저장될 수 없어야 한다 (ADR-002).

Scenario 3 (실패 흐름): 물리 삭제가 차단된다
- Given: 이미 참조된 `Place` 레코드가 있고
- When: 삭제 요청이 들어오면
- Then: 행을 지우지 않고 `deletedAt` 만 갱신한다. 삭제 후에도 `Dish` 이력이 조회 가능해야 한다.

Scenario 4 (실패 흐름): 가격 표본이 부족한 매장이 식별된다
- Given: `sampleSize < 5` 인 `PriceProfile` 이 존재하고
- When: 해당 매장을 조회하면
- Then: `sampleSize` 만으로 '가격 확인 필요' 판정이 가능해야 한다. `QRY-007` 이 이 값으로 예상가 산출 여부를 정한다 (US-1 AC6).

Scenario 5 (실패 흐름): 금지된 컬럼이 스키마에 존재하지 않는다
- Given: 전체 스키마가 적용된 상태에서
- When: 컬럼 목록을 검사하면
- Then: `Proposal` 에 가격 협상 필드 0개, `Payment` 에 카드 정보 컬럼 0개여야 한다. **발견 시 `TST-008` 실패 (§6.3-7 · REQ-NF-011)**

## ⚙️ Technical & Non-Functional Constraints
- 성능: `canonicalKey` 인덱스가 **REQ-NF-002**(색인 조회 p95 ≤ 400ms)의 전제다. 누락 시 목표 달성이 불가능해진다.
- 안정성: 마이그레이션은 `prisma migrate deploy` 로만 적용하며 **빌드 단계에 넣지 않는다** (SRS §6.4 · §14.4).
- 보안: **REQ-NF-010** 개인 식별 정보를 두지 않는다. 회식 참석자의 비고·개인 취향 필드는 **스키마에 존재해서는 안 된다**.
- 기술 제약: **C-TEC-003** · **REQ-TEC-004** DB 접근은 `src/lib/db.ts` 싱글턴 경유만. **REQ-TEC-006** 로컬·운영 드리프트 0.
- 되돌림 비용: **ADR-001 기준 최대** — 색인 단위를 바꾸면 전면 재색인 + REQ-FUNC-002~005 전부 재작업. S0에서 확정하고 이후 변경하지 않는다.
