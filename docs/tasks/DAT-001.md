## 🎯 Summary
- 기능명: [DAT-001] Prisma 스키마 전체 — 엔터티 · `Verification` · `Event` 파티셔닝 · `canonicalKey` 정규화 사전
- 목적: 색인의 기본 단위를 `Place`가 아니라 **`Dish` + `Attribute`** 로 고정하고, 근거 표기의 전제인 `Verification` 분리와 계측의 전제인 `Event` 파티셔닝까지 **`schema.prisma` 한 파일에서 확정**한다. 이 스키마가 없으면 나머지 전 기능이 얹힐 바닥이 없다.
- ⚠️ **v3.0 축약으로 `DAT-002`(속성·검증) · `DAT-003`(대화방·예약·결제) · `DAT-004`(이벤트) · `DAT-005`(정규화 사전)를 흡수했다.** 전부 같은 파일을 만지므로 한 PR로 처리한다.

## ✅ Task Breakdown (실행 계획)
- [ ] `prisma/schema.prisma` 에 `datasource` 블록 작성 — `url = env("DATABASE_URL")`(Supavisor :6543), `directUrl = env("DIRECT_URL")`(:5432). 두 값 분리는 REQ-TEC-005 검사 대상
- [ ] `Place` 모델 정의 — `id`(uuid PK) · `name` · `districtCode` · `seats` · `maxParty` · `latitude` · `longitude` · `deletedAt`(nullable, 논리 삭제)
- [ ] `Dish` 모델 정의 — `id` · `placeId`(FK) · `name` · `canonicalKey` · `price`. **`canonicalKey` 단독 인덱스 필수**
- [ ] `PriceProfile` 모델 정의 — `placeId`(unique FK) · `perPersonLow` · `perPersonHigh` · `sampleSize`. **단일 값 컬럼(`perPersonAvg` 단독)을 두지 않는다**
- [ ] 인덱스 추가 — `Place`: `@@index([districtCode, deletedAt])` / `Dish`: `@@index([canonicalKey])`
- [ ] `prisma migrate dev --name init_place_dish_price` 로 로컬 Supabase에 마이그레이션 생성·적용
- [ ] `src/lib/db.ts` 싱글턴에서 세 모델이 타입 추론되는지 확인 (`prisma generate` 후 `tsc --noEmit`)
- [ ] `Attribute` 모델 정의 — `ownerId` · `scope`(PLACE/DISH) · `key` · `value`. **성분·접근성 필드를 같은 테이블에 사전 확보**(REQ-FUNC-010). `@@index([ownerId, scope, key])`
- [ ] `Verification` 모델을 **별도 엔터티로 분리** — `attributeId`(unique) · `status` · `verifiedAt` · `verifiedBy` · `sourceUrl`. `@@index([verifiedAt])` (90일 스캔용 · ADR-002)
- [ ] `AgentRoom` · `Proposal` · `Reservation` · `Payment` 모델 정의 — `Proposal` 에 **가격 필드를 두지 않고**, `Payment` 에 **카드 정보 컬럼을 두지 않는다**. `Payment.idempotencyKey` unique
- [ ] `Event` 모델 정의 — `eventId`(PK · 중복 제거 키) · `occurredAt` · `receivedAt` · `properties` · `incomplete`
- [ ] `Event` **일 단위 파티셔닝 원시 SQL 마이그레이션** 작성 (Prisma 스키마로 표현 불가)
- [ ] `canonicalKey` **정규화 사전 및 정규화기** 구현 — '물냉면/평양냉면/냉면'을 동일 키로 묶는 규칙
- [ ] 시드 스크립트 작성 — 상권 1곳 기준 최소 표본(가격 표본 5건 이상 매장 / 5건 미만 매장 각 1건 이상 포함, 90일 초과 속성 1건 포함)
- [ ] 단위 테스트 작성 — 논리 삭제 시 `deletedAt` 만 갱신되고 행이 남는지, `canonicalKey` 로 서로 다른 `Place` 의 `Dish` 가 함께 조회되는지
- [ ] 통합 지점 검증 — `prisma migrate deploy` 가 운영 Supabase에서 드리프트 없이 적용되는지 (REQ-TEC-006)

## 🧪 Acceptance Criteria (BDD/GWT)

Scenario 1: 메뉴명 정규화 키로 여러 매장이 함께 조회된다
- Given: `canonicalKey = "냉면"` 을 공유하는 `Dish` 가 서로 다른 세 개의 `Place` 아래에 적재되어 있고,
- When: `canonicalKey` 로 `Dish` 를 조회하면,
- Then: 세 매장의 `Dish` 가 모두 반환되고, 조회는 `@@index([canonicalKey])` 를 사용한다. `EXPLAIN` 결과에 Seq Scan이 없어야 한다.

Scenario 2: 인당 예상가는 범위로만 저장된다
- Given: `PriceProfile` 스키마가 적용된 상태에서,
- When: `perPersonLow` 또는 `perPersonHigh` 없이 단일 값만으로 레코드를 생성하려 하면,
- Then: Prisma 타입 검사 단계에서 실패한다. **단일 값 저장 경로가 존재하지 않아야 한다** (SRS §6.2 주요 필드 규칙).

Scenario 3 (실패 흐름): 물리 삭제가 차단된다
- Given: 이미 참조된 `Place` 레코드가 있고,
- When: 삭제 요청이 들어오면,
- Then: 행을 지우지 않고 `deletedAt` 만 갱신한다. 삭제 후에도 해당 `Place` 의 `Dish` 이력이 조회 가능해야 한다 (SRS §6.4 논리 삭제).

Scenario 4 (실패 흐름): 가격 표본이 부족한 매장이 식별된다
- Given: `sampleSize < 5` 인 `PriceProfile` 이 존재하고,
- When: 해당 매장을 조회하면,
- Then: `sampleSize` 값으로 **'가격 확인 필요' 판정이 가능**해야 한다. 후속 태스크(QRY-007)가 이 값만으로 예상가 산출 가능 여부를 판단할 수 있어야 한다 (US-1 AC6).

Scenario 5: 속성마다 확인 이력이 정확히 하나 붙는다
- Given: `Attribute` 와 `Verification` 이 1:1로 정의된 상태에서,
- When: 속성을 조회하면,
- Then: `verifiedAt` · `verifiedBy` 가 반드시 함께 조회된다. 확인 이력 없는 속성이 저장될 수 없어야 한다 (ADR-002 · 근거 표기의 구조적 전제).

Scenario 6 (실패 흐름): 금지된 컬럼이 스키마에 존재하지 않는다
- Given: 전체 스키마가 적용된 상태에서,
- When: 컬럼 목록을 검사하면,
- Then: `Proposal` 에 **가격 협상 필드가 0개**, `Payment` 에 **카드 정보 컬럼이 0개**여야 한다. 하나라도 발견되면 실패한다 (SRS §6.3-7 · REQ-NF-011).

## ⚙️ Technical & Non-Functional Constraints
- 성능: `Dish` 의 `canonicalKey` 조회가 REQ-NF-002(색인 조회 p95 ≤ 400ms)의 전제다. 인덱스 누락 시 이 목표가 달성 불가능해진다.
- 안정성: 마이그레이션은 `prisma migrate deploy` 로만 적용하며 **빌드 단계에 넣지 않는다** (SRS §6.4 · §14.4 — 롤백이 어려운 스키마 변경의 자동 적용 방지).
- 보안·개인정보: 이 스키마에는 개인 식별 정보를 두지 않는다. 회식 참석자의 비고·개인 취향 필드는 **스키마에 존재해서는 안 된다** (REQ-NF-010).
- 기술 제약: **C-TEC-003** — Prisma + Supabase. **REQ-TEC-004** DB 접근은 `src/lib/db.ts` 싱글턴 경유만 허용. **REQ-TEC-005** `DATABASE_URL`(Supavisor :6543) / `DIRECT_URL`(:5432) 분리 필수. **REQ-TEC-006** 로컬·운영 스키마 드리프트 0.
- 되돌림 비용: **ADR-001 기준 최대**. 색인 단위를 바꾸면 전면 재색인 + REQ-FUNC-002~005 전부 재작업. S0에서 확정하고 이후 변경하지 않는다.
