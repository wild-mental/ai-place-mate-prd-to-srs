## ✅ Task Breakdown (실행 계획)
- [ ] 콘솔 전체 구조 설계 — **설정 화면 ≤ 3개**
- [ ] 프로필 입력 화면 — 분위기·강점·서비스·수용 조건. **필수 항목 ≤ 5개**
- [ ] 근거 없는 문구 안내 UI — 저장이 거부됐을 때 **무엇을 등록해야 하는지** 알려 주는 화면 (US-5 AC4)
- [ ] 1회 클릭 재편집 — 기존 항목을 불러오는 동선 (US-5 AC3)
- [ ] 소환 알림 수신 화면 — 조건과 남은 시간이 한눈에
- [ ] 제안 작성 화면 — 강점을 적는 곳이지 **할인폭을 적는 곳이 아님**을 시각적으로 명확히
- [ ] 검색 화면과 다른 레이아웃 언어 — 역할이 다름을 시각으로 구분
- [ ] 핸드오프 — `MCH-002` 구현 규격

## 🧪 Acceptance Criteria (BDD/GWT)

Scenario 1: 설정이 3개 화면 안에서 끝난다
- Given: 콘솔 구조가 설계된 상태에서
- When: 화면 수를 세면
- Then: 설정 화면이 3개를 넘지 않고 필수 항목이 5개를 넘지 않는다. **설정 화면 ≤ 3개 · 필수 항목 ≤ 5개 (US-5 AC1)**

Scenario 2 (실패 흐름): 근거 없는 문구가 거부될 때 다음 행동을 안내한다
- Given: 사장이 뒷받침되지 않는 강점 문구를 입력하고
- When: 저장이 거부되면
- Then: **어떤 속성을 등록해야 하는지** 구체적으로 안내한다. 거부만 하고 끝내면 사장이 이탈한다.

## ⚙️ Technical & Non-Functional Constraints
- 사용자 특성: **P5는 조작 숙련도가 낮다**(SRS §8) — 화면 수 상한이 이탈 방어의 핵심이다.
- 설계 원칙: **할인폭을 넣는 칸이 아니다** — 경쟁 축은 가격이 아니라 조건 적합도(§6.3-7).
- 리스크: **R1** 매장 참여 미달이 이 제품의 최대 리스크다. 콘솔 UX가 참여율을 좌우한다.
