## 🧪 Acceptance Criteria (BDD/GWT)

Scenario 1: 이벤트 20종이 스키마로 검증된다
- Given: 이벤트 계약이 정의된 상태에서
- When: 각 이벤트의 유효 페이로드를 검증하면
- Then: 20종 전부 통과하고 SRS §10.2.2 표의 필수 속성이 모두 존재한다. **누락 0종**

Scenario 2: 경로 태깅 속성이 존재한다
- Given: `top3_rendered` 스키마가 정의된 상태에서
- When: 속성 목록을 검사하면
- Then: `parse_path` 가 필수 속성으로 존재한다. 이 값이 없으면 **REQ-NF-001a와 001b를 분리 측정할 수 없다**.

Scenario 3 (실패 흐름): 필수 속성이 빠진 이벤트가 표기된다
- Given: 필수 속성 하나가 결측된 이벤트가 주어지고
- When: 검증을 실행하면
- Then: 이벤트를 폐기하지 않고 `incomplete: true` 로 표기해 적재한다. `ANA-005` 의 결측률 집계 대상이 된다. **결측률 ≤ 1%**

## ⚙️ Technical & Non-Functional Constraints
- 계측 원칙: **중복 제거는 애플리케이션이 아니라 스키마가 보장한다** — `event_id` 를 기본 키로 두어 DB 제약으로 이중 계수를 차단한다 (SRS §10.2).
- 성능: 계측은 사용자 요청 경로의 지연 원인이 되면 안 된다. 스키마 검증은 수집 엔드포인트(`ANA-002`)에서 수행하고 렌더 경로에 넣지 않는다.
- 보안: **REQ-NF-010** 이벤트 속성에 개인 식별 정보를 담지 않는다. 좌표·연락처를 속성으로 두지 않는다.
