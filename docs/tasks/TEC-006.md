## ✅ Task Breakdown (실행 계획)
- [ ] `verify-constraints.mjs` 에 검사 추가 — `package.json` 의존성에 메시지 브로커 클라이언트가 없는지 (kafkajs · @aws-sdk/client-sqs · bullmq · amqplib 등)
- [ ] 허용 수단 명문화 — 응답 이후 처리는 `after()`, 지연·재시도가 필요하면 **DB 큐 테이블**

- [ ] 기존 큐 성격 테이블(`ReverifyTask`)이 규약을 따르는지 점검 (`DAT-010` 과 교차)
- [ ] 단위 테스트 — 금지 의존성을 추가했을 때 검사가 실패하는지

## 🧪 Acceptance Criteria (BDD/GWT)

- Given: 비동기 처리가 `after()` 또는 DB 큐 테이블로 구현된 상태에서
- When: 빌드를 실행하면
- Then: 제약 검사를 통과한다.

Scenario 2 (실패 흐름): 외부 브로커 의존성이 빌드를 막는다
- Given: `package.json` 에 메시지 브로커 클라이언트를 추가한 상태에서
- When: 빌드를 실행하면
- Then: `verify-constraints` 가 해당 패키지명을 지목하고 **빌드가 실패**한다. **브로커 의존성 0개 (REQ-TEC-014 · D-04)**

## ⚙️ Technical & Non-Functional Constraints
- 기술 제약: **D-04** Kafka·SQS를 도입하지 않는다. **REQ-TEC-014** 응답 이후 처리는 `after()` 또는 DB 큐 테이블로만 구현한다.
- 대가: 큐가 없어 대량 유입 시 DB 쓰기 부하가 발생한다(SRS §15-10). 부하는 `REL-003`(풀 사용률)에서 감시한다.
