## ✅ Task Breakdown (실행 계획)
- [ ] 색인 적재 파이프라인 — `Place` → `Dish`(정규화 키 부여) → `Attribute` → `Verification` 순으로 적재
- [ ] 적재 시 `canonicalKey` 정규화기(`DAT-001`) 적용 및 미매칭 메뉴명 로그 수집 (사전 확장 재료)
- [ ] 속성 조회 API 설계 — `queryByAttribute(AttributeQuery)` 형태로 `query` 모듈에 노출
- [ ] `src/lib/cache.ts` — `use cache` 래퍼 작성. `cacheTag` 로 무효화 단위를 `place:{id}` · `district:{code}` 로 분리
- [ ] `cacheLife` 설정 — 속성·메뉴 조회 TTL 6시간 (SRS §6.1 캐시 TTL)
- [ ] 변경 시 무효화 — 적재·재확인 처리 후 `updateTag` 호출
- [ ] 캐시 히트율 계측 — 히트/미스를 이벤트로 적재해 `ANA-002` 가 집계
- [ ] 커버리지 리포트 — 상권별 필수 필드 5개 충족 매장 수 산출 (목표 300곳 · R2 추적)
- [ ] 단위 테스트 — 캐시 히트 시 DB 호출이 발생하지 않는지, 무효화 후 최신값이 나오는지

## 🧪 Acceptance Criteria (BDD/GWT)

Scenario 1: 캐시 히트 시 DB를 조회하지 않는다
- Given: 속성이 캐시에 적재된 상태에서
- When: 동일 키로 다시 조회하면
- Then: DB 호출 없이 반환되고 응답이 목표 안에 든다. **캐시 히트 시 p95 ≤ 120ms (REQ-NF-002)**

Scenario 2: 변경 후 최신값이 반영된다
- Given: 캐시에 적재된 속성이 재확인으로 갱신되고
- When: `updateTag` 가 호출된 뒤 조회하면
- Then: 갱신된 값이 반환된다. 오래된 값이 계속 나오면 안 된다.

Scenario 3 (실패 흐름): 커버리지 미달이 드러난다
- Given: 상권의 필수 필드 5개 충족 매장이 300곳 미만이고
- When: 커버리지 리포트를 산출하면
- Then: 상권별 부족 수치가 보고되고 `ANA-005` 의 알림 대상이 된다. 부족을 감춘 채 결과를 내보내지 않는다. **상권당 < 300곳 시 알림 (R2)**

## ⚙️ Technical & Non-Functional Constraints
- 성능: **REQ-NF-002** 색인 조회 p95 ≤ 400ms · 캐시 히트 시 ≤ 120ms · 히트율 ≥ 70%.
- 기술 제약: **D-03 · REQ-TEC-015** 외부 캐시 서버를 도입하지 않는다. 캐시는 Next.js `use cache` 와 PostgreSQL로만 구현한다 (ADR-T05).
- 한계: **LIM-T02** 캐시 무효화가 태그 단위로만 가능하다. 키 단위 세밀 제어가 필요하면 태그 설계를 다시 나눠야 한다.
- 되돌림 비용: 중간 — 태그 설계를 바꾸면 무효화 호출 지점을 전부 손봐야 한다.
