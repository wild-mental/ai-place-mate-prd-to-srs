## 🧪 Acceptance Criteria (BDD/GWT)

Scenario 1: 유효 입력이 타입 안전하게 통과한다
- Given: `submitQuery` 의 입력 스키마가 정의된 상태에서
- When: 자연어 1줄·지역·인원을 담은 유효 입력을 파싱하면
- Then: `z.infer` 로 추출한 타입과 런타임 결과가 일치하고 반환은 `ActionResult<...>` 다. **tsc 경고 0건**

Scenario 2: 소환 0곳이 실패가 아닌 정상 응답이다
- Given: `createAgentRoom` 의 출력 계약이 정의된 상태에서
- When: 적합 매장이 0곳인 결과를 표현하면
- Then: `ok: true` 이면서 소환 수 0과 미개시 사유를 담을 수 있다. 오류로 표현하면 '빈 화면 금지'(§6.3-6)를 구현할 수 없다.

Scenario 3 (실패 흐름): 무효 입력이 스택 노출 없이 거부된다
- Given: `requestPayment` 에 `reservationId` 가 누락된 입력이 주어지고
- When: 입력 검증이 실행되면
- Then: 예외를 던지지 않고 `{ ok: false, code, message }` 를 반환한다. 응답에 스택·내부 경로·SQL이 포함되어서는 안 된다.

Scenario 4 (실패 흐름): 개인 식별 정보 필드가 계약에 없다
- Given: 9종 입력 스키마 전체가 정의된 상태에서
- When: 스키마 키 집합을 검사하면
- Then: 참석자 연락처·개인 취향·비고에 해당하는 필드가 0개여야 한다. **발견 시 테스트 실패 (REQ-NF-010)**

## ⚙️ Technical & Non-Functional Constraints
- 성능: 입력 검증은 요청 경로 맨 앞에 있으므로 **REQ-NF-001a**(p95 ≤ 1,000ms) 예산을 잠식하지 않아야 한다. 스키마 컴파일은 모듈 로드 시 1회만.
- 안정성: 모든 실패를 `ActionResult` 로 표현해 5xx로 새지 않게 한다. **REQ-NF-006** 5xx ≤ 0.3% — 검증 실패는 5xx가 아니다.
- 보안: **REQ-NF-010** 개인 제약 정보는 계약에 필드를 두지 않는다. **SRS §6.1 규약 ②** Server Action은 공개 엔드포인트와 동등하므로 인가를 첫 줄에서 확인한다.
- 기술 제약: **C-TEC-002** · **REQ-TEC-002** 계약은 `src/contracts/index.ts` 로만 노출. **REQ-TEC-010** LLM 응답은 이 스키마 검증을 통과해야만 사용한다.
