## 🧪 Acceptance Criteria (BDD/GWT)

Scenario 1: Cron 엔드포인트가 정상 호출을 처리한다
- Given: `CRON_SECRET` 이 설정되고 계약이 정의된 상태에서
- When: Vercel Cron이 올바른 시크릿과 함께 호출하면
- Then: 처리 건수·소요 시간·마지막 실행 시각을 담은 응답을 반환한다. 5종이 동일한 형태여야 한다.

Scenario 2: 폴백 신호가 오류로 집계되지 않는다
- Given: 에러 코드 체계가 정의된 상태에서
- When: 파싱 실패·결과 0건·제안 0건 신호를 분류하면
- Then: 셋 다 **폴백 신호**로 분류되고 5xx가 아니다. `REL-007` 의 오류율 집계에서 제외된다 (§6.3-6).

Scenario 3 (실패 흐름): 서명 없는 웹훅이 본문 파싱 전에 거부된다
- Given: `PG_WEBHOOK_SECRET` 이 설정된 상태에서
- When: 서명이 없거나 불일치하는 요청이 도착하면
- Then: **본문을 파싱하기 전에** 거부한다. 응답에 내부 상태·스택이 포함되지 않아야 하고 결제 오류율 예산에 5xx로 집계되지 않아야 한다. **결제 API 5xx ≤ 0.1%**

Scenario 4 (실패 흐름): 외부에서 Cron 엔드포인트를 실행할 수 없다
- Given: `/api/cron/purge` 가 배포된 상태에서
- When: `CRON_SECRET` 없이 외부에서 호출하면
- Then: 인증 거부로 응답하고 **개인정보 파기 로직이 실행되지 않는다**. **무단 실행 0건 (REQ-TEC-013 · REQ-NF-010)**

Scenario 5 (실패 흐름): 근거 4항목이 없는 공유 카드는 만들어지지 않는다
- Given: 근거 4항목 중 하나가 누락된 후보 id가 주어지고
- When: `/api/share-cards/[id]` 를 호출하면
- Then: 이미지를 생성하지 않고 **400**을 반환한다. 빈 이미지나 플레이스홀더를 반환해서는 안 된다.

## ⚙️ Technical & Non-Functional Constraints
- 성능: `/api/share-cards/[id]` 는 GET 캐시가 가능한 유일한 경로다. 캐시 헤더 계약이 **REQ-FUNC-005** 생성 p95 ≤ 3,000ms 달성 수단이다.
- 안정성: **REQ-NF-006** 5xx ≤ 0.3% · 결제 ≤ 0.1%. 인증·검증 실패는 4xx이며 5xx로 집계되지 않아야 한다.
- 보안: **REQ-NF-011** 웹훅은 서명 검증 후에만 처리하고 카드 정보를 수신·보관하지 않는다. **REQ-TEC-013** Cron은 외부 호출을 거부한다.
- 설계 원칙: **폴백은 오류가 아니다.** 파싱 실패·결과 0건·제안 0건은 열화된 정상 흐름이므로 오류율 예산에 집계되면 안 된다.
