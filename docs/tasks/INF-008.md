## 🧪 Acceptance Criteria (BDD/GWT)

Scenario 1: 모든 요청에 상관 ID가 부여된다
- Given: `proxy.ts` 가 배포된 상태에서
- When: 임의의 요청이 들어오면
- Then: 요청 ID가 발급되고 응답 헤더와 로그에 동일한 값이 남아 추적이 가능하다.

Scenario 2 (실패 흐름): 미인증 상태로 가맹 콘솔에 접근할 수 없다
- Given: 세션이 없는 상태에서
- When: `/(merchant)` 경로에 접근하면
- Then: 핸들러 실행 전에 차단되고 로그인으로 유도된다. 콘솔 데이터가 응답에 포함되어서는 안 된다. **비인가 노출 0건 (REQ-NF-012)**

## ⚙️ Technical & Non-Functional Constraints
- 성능: 프록시는 모든 요청 경로에 있으므로 **REQ-NF-001a**(결정론 경로 p95 ≤ 1,000ms) 예산을 잠식하지 않아야 한다. 동기 I/O를 넣지 않는다.
- 기술 제약: **C-TEC-002** 서버 로직은 RSC · Server Action · Route Handler로만 구현한다. 프록시는 라우팅 계층이며 비즈니스 로직을 두지 않는다.
- 보안: **REQ-NF-012** 내부 조회는 감사 로그 대상이다. 프록시가 붙인 상관 ID가 `audit_logs` 와 연결되어야 한다.
