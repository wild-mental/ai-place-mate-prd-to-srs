## 🧪 Acceptance Criteria (BDD/GWT)

Scenario 1: 승인 후 매장에 확정이 통보된다
- Given: 결제 승인이 완료되고
- When: 웹훅이 도착하면
- Then: 예약이 `CONFIRMED` 로 전이되고 매장에 확정이 통보된다. **통보 지연 ≤ 30s (US-4 AC2)**

Scenario 2 (실패 흐름): 중복 웹훅에도 상태가 변하지 않는다
- Given: 동일한 멱등 키의 웹훅이 이미 처리된 상태에서
- When: 같은 키로 다시 도착하면
- Then: 재처리하지 않고 최초 결과를 반환한다. `Payment` 상태가 바뀌어서는 안 된다. **중복 처리 0건 (SRS §9.2)**

Scenario 3 (실패 흐름): 서명 없는 웹훅이 본문 파싱 전에 거부된다
- Given: 서명 헤더가 없거나 불일치하는 요청이 도착하고
- When: 핸들러가 실행되면
- Then: 본문을 파싱하기 전에 거부한다. 결제 API 오류율에 5xx로 집계되지 않아야 한다. **결제 API 5xx ≤ 0.1% (REQ-NF-006)**

Scenario 4 (실패 흐름): 카드 정보가 저장되지 않는다
- Given: 결제 흐름 전체가 실행된 뒤
- When: `Payment` 테이블을 검사하면
- Then: 카드 정보 컬럼이 존재하지 않고 `pgTransactionId` 만 보관된다. **카드 정보 저장 0건 (REQ-NF-011)**

## ⚙️ Technical & Non-Functional Constraints
- 보안: **REQ-NF-011** PCI-DSS 준수 PG 위탁 · 카드 정보 비보관 · 저장 AES-256 · 전송 TLS 1.3 · 웹훅 서명 검증 필수.
- 안정성: **REQ-NF-006** 결제 API 5xx ≤ 0.1%. 서명·검증 실패는 4xx다.
- 기술 제약: **C-TEC-002** 결제 요청은 Server Action, 결과 수신은 Route Handler 웹훅 — 외부에서 들어오기 때문이다(SRS §15-9).
- 멱등성: 서버리스에서 웹훅 중복은 예외가 아니라 기본 가정이다. DB unique 제약으로 보장하고 애플리케이션 로직에 의존하지 않는다.
