## ✅ Task Breakdown (실행 계획)
- [ ] `src/mocks/` 생성 — 픽스처는 `CTR-001` · `CTR-002` 계약 타입을 그대로 만족해야 한다
- [ ] **Top-3 픽스처** — 정상 3건 / 근거 4항목 중 하나 누락 / 후보 2건 이하 / 후보 0건
- [ ] **파싱 픽스처** — 캐시 히트 / 결정론 성공 / LLM 폴백 / 파싱 실패(구조화 필터 전환)
- [ ] **대화방·제안 픽스처** — 제안 0건 / 1건 / 5건 / 마감 경과 / 소환 0곳 미개시
- [ ] **결제·웹훅 픽스처** — 승인 / 거절 / 중복 수신(멱등) / 환불 / 노쇼
- [ ] Mock 모드 스위치 — 환경 변수로 활성화하며 **로컬·프리뷰에서만** 동작. 프로덕션에서는 강제 비활성
- [ ] 타입 계약 테스트 — 픽스처가 계약 스키마를 통과하는지 (계약 변경 시 픽스처가 먼저 깨지게)
- [ ] 단위 테스트 — 프로덕션 환경에서 Mock 모드가 켜지지 않는지

## 🧪 Acceptance Criteria (BDD/GWT)

Scenario 1: 픽스처가 계약 스키마를 만족한다
- Given: `CTR-001` · `CTR-002` 의 스키마가 정의된 상태에서
- When: 전체 픽스처를 검증하면
- Then: 모두 통과한다. 계약이 바뀌면 픽스처 테스트가 먼저 실패해 불일치를 조기에 드러낸다. **불일치 0건**

Scenario 2: 실패·경계 상태를 픽스처로 재현할 수 있다
- Given: Mock 모드가 활성화된 상태에서
- When: 근거 누락·제안 0건·웹훅 중복 시나리오를 요청하면
- Then: 해당 상태가 그대로 재현되어 UI가 실패 흐름을 개발·검증할 수 있다.

Scenario 3 (실패 흐름): 프로덕션에서 Mock 모드가 켜지지 않는다
- Given: 프로덕션 배포 환경에서
- When: Mock 모드 환경 변수를 설정해도
- Then: 스위치가 강제 비활성되고 실제 데이터 경로만 동작한다. 가짜 데이터가 사용자에게 노출되어서는 안 된다. **프로덕션 Mock 응답 0건**

## ⚙️ Technical & Non-Functional Constraints
- 기술 제약: **C-TEC-002** 별도 Mock 서버를 세우지 않는다. 픽스처는 앱 내부 모듈로 두고 환경 변수로만 전환한다.
- 보안: 픽스처에 실제 매장·이용자 데이터를 넣지 않는다. 전부 합성 데이터여야 한다.
- 품질: 픽스처는 **정상보다 실패·경계를 더 많이** 담는다 — 그쪽이 실제 데이터로 만들기 어려운 쪽이기 때문이다.
