## ✅ Task Breakdown (실행 계획)
- [ ] **US-4** — AC1 조건 승계(재입력 0개) · AC2 주문량 금액 산출·통보 · **AC3 취소·환불** · **AC4 노쇼 판정**
- [ ] **멱등성 테스트** — 동일 멱등 키 웹훅을 2회·3회 전송해도 `Payment` 상태가 변하지 않는지
- [ ] 서명 검증 테스트 — 서명 없음·불일치·만료 3종이 전부 거부되는지
- [ ] 거부 응답이 4xx인지 확인 — 5xx로 새면 결제 오류율 예산(0.1%)이 오염된다
- [ ] 매장 귀책 분기 테스트 — 노쇼 오판정이 발생하지 않는지
- [ ] 픽스처 사용 — `MCK-001` 의 결제·웹훅 픽스처 (승인/거절/중복/환불)

## 🧪 Acceptance Criteria (BDD/GWT)

Scenario 1: US-4의 정상 AC가 통과한다
- Given: 결제 픽스처가 준비된 상태에서
- When: 테스트를 실행하면
- Then: 조건 승계와 금액 산출·통보 AC가 통과한다. **재입력 0개 · 통보 ≤ 30s**

Scenario 2 (실패 흐름): 중복 웹훅이 상태를 바꾸지 못한다
- Given: 동일 멱등 키 웹훅을 3회 전송하고
- When: 테스트가 상태를 검사하면
- Then: `Payment` 상태가 최초 처리 결과 그대로여야 한다. 이중 정산이 발생하면 실패한다. **중복 처리 0건**

Scenario 3 (실패 흐름): 서명 실패가 4xx로 처리된다
- Given: 서명이 불일치하는 웹훅을 전송하고
- When: 응답을 검사하면
- Then: 4xx이며 5xx가 아니다. 5xx면 결제 오류율 예산이 잘못 소모된다. **결제 5xx ≤ 0.1%**

## ⚙️ Technical & Non-Functional Constraints
- 품질: US-4의 AC 4건 전부 커버. **실패 흐름 2건**(AC3 취소·AC4 노쇼) 포함.
- 보안: **REQ-NF-011** 서명 검증·카드 정보 비보관을 테스트로 고정한다.
- 멱등성: 중복 웹훅 테스트는 **선택이 아니라 필수**다 — 서버리스에서 중복은 반드시 발생한다.
