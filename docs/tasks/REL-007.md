## ✅ Task Breakdown (실행 계획)
- [ ] Vercel Runtime Logs 연동 — 5분 윈도 집계
- [ ] 상태 코드 분류 — `CTR-002` 의 에러 코드 → HTTP 매핑표를 집계 기준으로 사용
- [ ] **폴백 신호 제외** — 파싱 실패·결과 0건·제안 0건은 오류율 분자에서 뺀다 (§6.3-6)
- [ ] 결제 API 별도 집계 — `/api/webhooks/pg` 및 결제 Server Action은 더 엄격한 임계
- [ ] 임계 알림 — 5분 5xx > 0.3%(일반) / > 0.1%(결제) 시 PagerDuty
- [ ] 4xx 별도 추적 — 인증·검증 실패는 오류율이 아니라 **품질 신호**로 본다
- [ ] 단위 테스트 — 폴백 신호가 분자에 포함되지 않는지, 결제 임계 분리

## 🧪 Acceptance Criteria (BDD/GWT)

Scenario 1: 오류율이 임계 안에서 유지된다
- Given: 정상 운영 상태에서
- When: 5분 윈도 집계가 실행되면
- Then: 5xx 오류율이 임계 이하로 산출된다. **일반 ≤ 0.3% · 결제 ≤ 0.1% (REQ-NF-006)**

Scenario 2 (실패 흐름): 폴백 신호가 오류로 집계되지 않는다
- Given: 파싱 실패·결과 0건·제안 0건이 다수 발생한 상태에서
- When: 오류율을 집계하면
- Then: 이들은 분자에서 제외된다. 설계된 열화 경로를 장애로 보고하면 잘못된 대응을 부른다. **폴백 신호의 5xx 집계 0건 (§6.3-6)**

Scenario 3 (실패 흐름): 결제 오류가 별도 임계로 감시된다
- Given: 결제 API 5xx가 0.15%인 상태에서
- When: 집계가 완료되면
- Then: 일반 임계(0.3%)는 넘지 않았어도 **결제 임계(0.1%)를 넘어 알림**이 발송된다.

## ⚙️ Technical & Non-Functional Constraints
- 안정성: **REQ-NF-006** 5xx ≤ 0.3% · 결제 API ≤ 0.1%. 인증·검증 실패는 4xx이며 오류율이 아니다.
- 설계 원칙: **폴백은 오류가 아니다** — `CTR-002` 의 에러 코드 체계가 이 구분의 근거다.
- 의존: 집계 기준이 `CTR-002` 의 HTTP 매핑표다. 매핑이 바뀌면 이 집계도 함께 바뀌어야 한다.
