## ✅ Task Breakdown (실행 계획)
- [ ] 카운트다운 표시 — **서버가 내려준 마감 시각 기준**임을 전제로 설계
- [ ] 대기 중 화면 — 몇 곳이 소환됐는지, 몇 건이 도착했는지 실시간 표시 (대기 이탈 방어)
- [ ] 제안 도착 애니메이션 — 도착 순서가 아니라 **적합도 순 정렬**임을 오해 없게
- [ ] 제안 비교 레이아웃 — 분위기·강점·서비스를 같은 축으로
- [ ] **근거 표기** — 각 제안이 어떤 등록 속성에 근거하는지 (§6.3-2)
- [ ] 가격 비교 UI를 만들지 않는다 — 흥정으로 읽힐 여지를 시각에서 제거
- [ ] 제안 0건 복귀 화면 — `UX-004` 규격 재사용
- [ ] 핸드오프 — `AGR-003` · `AGR-006` 구현 규격

## 🧪 Acceptance Criteria (BDD/GWT)

Scenario 1: 대기 중 상태가 보인다
- Given: 대화방이 생성되고 카운트다운이 시작된 상태에서
- When: 화면을 보면
- Then: 소환된 매장 수와 도착 제안 수, 남은 시간이 표시된다. **대기 중 이탈 ≤ 15%**

Scenario 2: 제안이 적합도 순으로 비교된다
- Given: 제안이 여러 건 도착한 상태에서
- When: 비교 화면을 보면
- Then: 적합도 순으로 정렬되고 각 제안의 근거가 함께 표시된다. **근거 표기율 100% · 가격 비교 UI 0개 (US-6 AC3)**

Scenario 3 (실패 흐름): 제안 0건에도 화면이 비지 않는다
- Given: 180초가 지나고 제안이 0건인 상태에서
- When: 화면이 전환되면
- Then: 제안 없는 Top-3 복귀 화면이 렌더된다. **빈 제안 화면 노출 0건 (US-6 AC4)**

## ⚙️ Technical & Non-Functional Constraints
- 설계 원칙: **경쟁 축은 가격이 아니라 적합도**(§6.3-7) — 가격 비교 UI를 만들지 않는다.
- 성능: **US-6 AC2** 첫 제안 p50 ≤ 60s · 180초 내 도착률 85%. 대기 화면이 이탈률을 좌우한다.
- 기술 제약: 카운트다운은 **서버 마감 시각 기준**이다(ADR-T06) — 클라이언트 시계를 신뢰하지 않는 설계여야 한다.
