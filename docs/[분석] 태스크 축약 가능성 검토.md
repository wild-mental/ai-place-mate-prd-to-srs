**날짜:** 2026-08-25

**목표:** 태스크 수를 **50건 내외**로, 무리 없는 범위에서 축약

## 1. 결론

**축약 가능하다. 118건 → 56건 (감소 62건 · 53%)** 이 무리 없는 선이다.

> **개정 이력** — 초안은 53건이었으나 **UX 구현(프론트엔드)과 기능 구현(백엔드)이 4건 섞이는 문제**가 발견되어 56건으로 조정했다. 상세는 §4.4에 있다.

| 검사 | 결과 |
| --- | --- |
| 커버리지 | 118건 전부 배정 · 미배정 0 · 중복 0 |
| 병합 제약 위반 | **0건** (스프린트 span ≤ 2 · 구성원 ≤ 5 · 병합당 H ≤ 2 · Part 혼합 없음) |
| **구현 계층 혼합 (BE ↔ UI)** | **0건** (§4.4에서 교정) |
| 순환 의존성 | **0건** |
| 스프린트 역전 | **0건** |
| 의존 간선 | 188 → 114 (**−39%**) |

의존 간선이 39% 줄어드는 것이 이 축약의 실질 이득이다. 태스크 수보다 **관리해야 할 선후 관계가 줄어드는 것**이 더 크게 작용한다.

**56건을 권장하며, 50건까지 더 줄이는 것은 권하지 않는다.** 근거는 §5에 있다.

## 3. 병합 원칙 — "무리하지 않는 선"의 정의

아래 다섯 조건을 **전부** 만족할 때만 병합했다. 하나라도 어기면 병합하지 않았다.

| # | 조건 | 이유 |
| --- | --- | --- |
| **P1** | 스프린트 간격 2단계 이내 (병합 후 가장 늦은 스프린트로 배치) | 착수 시점이 크게 벌어지면 한 이슈가 스프린트를 넘어 열린 채 남는다 |
| **P2** | 구성원 5건 이하 | 6건 이상이면 리뷰 단위가 너무 커져 PR을 쪼갤 수 없다 |
| **P3** | 병합 결과의 H 복잡도 원본이 2건 이하 | H 두 개를 넘게 합치면 견적이 불가능해진다 |

| **P5** | 병합 후 순환·스프린트 역전이 생기지 않음 | 실행 순서가 깨진다 |
| **P6** | **BE(백엔드 로직)와 UI(프론트엔드 화면 구현)를 섞지 않음** | 담당자와 리뷰 관점이 다르고, UX 구현 진척을 별도로 볼 수 없게 된다 |

### 병합하지 않은 것 — 12건은 단독 유지

`INF-002` · `CTR-005` · `EVD-004` · `EVD-005` · `RNK-003` · `SEC-001` · `SEC-002` · `REL-004` · `TST-007` · `UX-013` · `UX-014` · `UX-015`

**독립된 인수 기준을 갖거나, 합치면 위 원칙을 어기는 것들**이다. 예를 들어 `SEC-001`(개인정보 30일 파기)과 `SEC-002`(프롬프트 개인정보 배제)는 같은 Epic이지만 산출물이 Cron과 프롬프트 필터로 전혀 다르다 — 합치면 하나가 끝나도 이슈를 닫을 수 없다.

### 4.4 구현 계층 분리 — UX 구현 vs 기능 구현

**Part A(개발·인프라)와 Part B(디자인)의 분리는 병합 전후 모두 완전히 유지된다 (혼합 0건).**
그러나 Part A **안에서** UX 구현(프론트엔드)과 기능 구현(백엔드)이 구분되지 않는 문제가 별도로 있었다.

원칙 **P6**을 신설하고 아래와 같이 재배치했다.

| 조치 | 내용 |

| `SEC-001` + `SEC-002` | 없음 (span 2) | 산출물이 파기 Cron과 프롬프트 필터로 무관. 하나가 끝나도 이슈를 닫을 수 없다 |
| `EVD-004` + `EVD-005` | 없음 (span 1) | 공유 카드 생성과 불일치 신고는 사용자 행동이 정반대. AC가 섞이면 리뷰가 어려워진다 |
| `REL-004` → `INF-003` | 없음 (span 1) | PITR 활성화는 Supabase 콘솔 설정이라 코드 PR이 없다. 코드 태스크에 섞으면 완료 판정이 흐려진다 |

**56과 50의 차이는 관리 부담에서 유의미하지 않다.** 반면 위 병합은 "이슈를 언제 닫을 수 있는가"를 흐리게 만든다. 요청하신 "50개 내외"에 56은 부합한다고 판단했다.

**더 줄이길 원하시면** 위 세 건을 적용해 정확히 50건으로 맞출 수 있다. 원칙 위반은 없으므로 판단만 주시면 된다.

## 6. 적용 시 영향

### 6.1 이미 작성한 이슈 문서 3건

대표 ID를 그룹 내 최소 번호로 잡아 **3건 모두 ID가 살아남는다.** 다만 범위가 넓어져 본문 보강이 필요하다.

| `CTR-001.md` | ID 유지 | `ConditionSet` 스키마 항목 추가 (**소폭**) |
| `CTR-002.md` | ID 유지 | 에러 코드 체계 항목 추가. `ErrorCode` "타입 자리만" 규약이 사라지므로 해당 문구 삭제 (**중간**) |

병합은 태스크를 **묶을 뿐 삭제하지 않으므로** 커버리지 손실은 없다. 다만 `관련 SRS 섹션` 열이 합쳐지면서 한 태스크가 여러 요구사항을 지시하게 되므로, **부록 C의 요구사항→태스크 매핑이 1:N에서 N:M으로 바뀐다.** 생성기가 자동 처리한다.

## 7. 권고

1. **56건 안을 적용한다.** 제약 위반·순환·역전·구현 계층 혼합이 전부 0건으로 검증된 안이다.
